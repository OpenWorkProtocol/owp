    WORKFLOW

    What this field lab exercises.

    The field lab follows a request through uncertainty, provider work, evidence, customer disposition, and handoff in one durable record.

    1

    Request

    The customer defines an outcome and a source. The field lab records a value signal, not a payment promise.

    2

    Accept or pass

    __OWP_OPERATOR_NAME__ makes an explicit provider decision. Passing is a valid terminal result; silence is not.

    3

    Attempt

    An accepted item starts a numbered attempt. PR state is refreshed so work begins against explicit current evidence.

    4

    Questions become durable decisions

    If a decision is needed, the customer sees options and evidence in the work thread. Their answer becomes part of the inherited state.

    5

    Delivery and validation

    The result is recorded with HTTPS evidence, then a separately named validation actor records valid or invalid with evidence.

    6

    Customer disposition

    Approve closes the work. Steer creates another attempt. Reject closes it. The customer can export the entire portable state at any point.

    PROTOCOL BOUNDARY

    Provider internals remain outside the portable boundary.

    __OWP_OPERATOR_NAME__ may use any agent runtime, orchestration system, human workflow, or combination. Those choices remain provider-internal; the shared boundary is the work record.

    Customer→Portable work↔__OWP_OPERATOR_NAME__ / agents→Evidence→Customer or next provider

    This is a public OWP field-lab profile. It is designed to exercise OWP concepts end to end; it does not claim independent implementation interoperability or full OWP 1.0 conformance.
