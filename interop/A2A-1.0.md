# A2A 1.0 interoperability note (informative)

Checked against the released A2A **1.0.0** specification on 2026-08-21.
Canonical reference: https://a2a-protocol.org/latest/specification/

OWP and A2A solve different layers. A2A transports conversations/tasks between
opaque agents; OWP records portable work state, operator decisions, and—when the
Software Work Integrity Profile is selected—the contract/provenance boundary.

Recommended mapping for software work:

- advertise an independent OWP extension URI such as
  `https://openworkprotocol.org/extensions/software-work-integrity/v1` in the
  Agent Card;
- request the extension with A2A's `A2A-Extensions` service parameter/header;
- carry `work_ref`, `contract_digest`, `attempt_id`, and
  `execution_commitment_digest` in typed extension metadata;
- let the A2A server generate `taskId` as A2A 1.0 requires; never overload a
  server-generated A2A task id with an OWP work ref or Attempt id;
- use A2A `contextId` only as conversational grouping. OWP work identity remains
  portable across A2A servers/providers and therefore cannot depend on one
  server's context id;
- treat A2A task completion as transport/execution status, not as OWP independent
  software validation. The validator attestation remains a separate proof.

A2A 1.0 supports asynchronous tasks, streaming, push notification, artifacts,
metadata, and extension URIs. Those features are useful transports for long OWP
Attempts but do not change OWP's validation semantics.
